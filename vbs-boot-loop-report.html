Windows Turning On VBS By Itself Is Causing Boot Loops

Error 0xc0000001 · Windows 11 · November 2026

Quick rundown

  • Windows turned VBS on by itself. The registry shows EnableVirtualizationBasedSecurity = 1 and WasEnabledBy = 1, with no group policy behind it.
  • On the next full boot, the boot loader loads the hypervisor and the secure kernel, then the PC resets before Windows starts.
  • After a few resets in a row, Windows shows 0xc0000001 "Your PC couldn't start properly ... After multiple tries".
  • Startup Repair finds nothing and there are no crash dumps, because the failure happens before Windows itself is running.
  • Turning VBS off in the registry from a recovery USB fixed every one.

Affected Computers

PCFirmwareWhat happened
Lenovo ThinkCentre M75s Gen 2 (AMD) 2021 BIOS Boot loop right after the logo. The boot loader failed while launching the hypervisor, error c000007b.
HP Laptop 17-cp3xxx (AMD) BIOS F.11 Windows turned VBS on 6 minutes after a good boot. Fast Startup hid it for days, until the first real restart.
Lenovo ThinkPad (type 21BW) N3MET29W 0xc0000001 "After multiple tries". Resets right after the hypervisor loads. Windows install was moved over from another PC.

What I found

1. The registry: Windows turned VBS on

Read from the ThinkPad's offline registry, from a recovery USB. The other two PCs showed the same values.

SYSTEM\ControlSet001\Control\DeviceGuard
CachedDrtmAuthIndex               = 01RequireMicrosoftSignedBootChain   = 12WasEnabledBy                      = 13EnableVirtualizationBasedSecurity = 1HyperVVirtualizationBasedSecurityOptout = 0VelocityScenarios\VbsCompatIssues = 0VelocityScenarios\HvciScanResult  = 0(no DeviceGuard group policy key)
  1. A stricter boot requirement that came on together with VBS.
  2. WasEnabledBy = 1 is the value Microsoft's own docs use when Windows (not a person or policy) turns the feature on.
  3. VBS is on. Nobody at the customer turned this on, and there is no group policy for it.

On the HP, the DeviceGuard key was last written at 5:40 PM on Nov 4, six minutes after the last good full boot at 5:34 PM.

The fix

Done offline from a WinPE / recovery USB, with the Windows drive as C:.

  1. Back up C:\Windows\System32\config\SYSTEM to the USB.
  2. Load the hive: reg load HKLM\OFF C:\Windows\System32\config\SYSTEM
  3. Under HKLM\OFF\ControlSet001\Control\DeviceGuard set:
    • EnableVirtualizationBasedSecurity = 0
    • RequireMicrosoftSignedBootChain = 0
    • Scenarios\HypervisorEnforcedCodeIntegrity\Enabled = 0
  4. Unload the hive: reg unload HKLM\OFF, then boot normally.
  5. Update the BIOS / UEFI firmware before letting VBS back on.

Turning off SVM / AMD-V (or Intel VT-x) in the BIOS also gets the PC booting, because it stops the hypervisor from loading. But that breaks WSL, Hyper-V and Sandbox, so the registry change is the better fix.

Has anyone else found this?

Partly. Microsoft has said that updates starting in October 2026 turn on memory integrity, and VBS with it, on more PCs. Separately, people are reporting 0xc0000001 boot loops after the November update (KB5132061). As of Nov 18, 2026 I couldn't find anyone who connected the two, or anyone who caught the hypervisor failing in a boot debugger. Microsoft does not list the boot loop as a known issue.

  • MC1465669: Expanding memory integrity protection across Windows devices Microsoft, Sept 1, 2026. Quality updates from October 2026 turn on memory integrity on eligible PCs, and on some PCs this also turns on VBS.
  • Windows 11 is now force-enabling Memory Integrity Windows Latest, Nov 11, 2026. Started in KB5127936 (Oct) and carried into KB5132061 (Nov).
  • Memory integrity enablement Microsoft Learn. Explains WasEnabledBy and EnabledBootId: a safeguard that turns memory integrity back off if the PC crashes during boot.
  • KB5132061 Boot Loop Nov 17, 2026. Reports of 0xc0000001 after KB5132061. An AMD ThinkPad booted again after SVM was turned off in the BIOS.
  • PC Won't Boot After KB5132061 Nov 2026. Reset right after the logo. Turning off Intel VT-x helped some users. VBS is not mentioned.
  • microsoft/WSL issue #40344 AMD board with older firmware gets 0xc0000001 whenever the hypervisor launches. A Microsoft staff member called it a likely driver / hypervisor issue.

Notes

  • Why the safeguard didn't help: Microsoft's auto-revert depends on Windows seeing a crash during boot. Here the PC resets before the Windows kernel ever starts, so Windows may never count it as a failed boot. I also didn't see an EnabledBootId value on the ThinkPad.
  • It hides for days: With Fast Startup on, shutting down is really hibernating, so the PC keeps resuming fine. The loop starts on the first real restart, often days after VBS was turned on.
  • Startup Repair won't find it: No crash dump and no event log entry, because Windows never starts. It may say a "recently serviced boot binary is corrupt", but the files are fine.
  • Secure Boot doesn't look like the trigger: The ThinkPad still reset with Secure Boot turned off.
  • Firmware looks like a factor: Two of the three are AMD PCs on older BIOS versions. I haven't confirmed whether a BIOS update alone fixes it.
  • Quick check from WinPE: If DeviceGuard\EnableVirtualizationBasedSecurity = 1 and WasEnabledBy = 1 on a PC that loops right after the logo, this is very likely the cause.
